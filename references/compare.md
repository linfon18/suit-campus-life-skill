# 食堂比价

## 触发

由模型结合本轮上下文识别比价意图，不要求用户明写“比价”，也不做固定关键词匹配。既保留“比价鸡排饭”“想吃牛肉面，帮我比价”等说法，也接受找最低价、询问哪里买更便宜或比较不同档口价格的同义表达。

| 用户表达示例 | 处理 |
|---|---|
| 哪里的鸡排饭最便宜？ / 鸡排饭去哪买更便宜？ | 比价鸡排饭，默认查询全部平台返回食堂 |
| 哪家牛肉面价格最低？ / 帮我找最便宜的肠粉 | 提取牛肉面 / 肠粉，进入比价，无需再确认是否比较 |
| 全校最便宜零食 / 哪里饮料最便宜 | 类别查询；全量采集后由模型判断符合项并排序，不把类别塞进 `--dish` |
| 全校最贵的食品 / 哪家牛肉面最贵 | 同样全量采集并审阅，按明确的价格口径降序；状态分别说明 |
| A、B 食堂哪边的鸡排饭便宜？ | 仅比较明确指定的 A、B 食堂，保留菜名和规格 |
| B 食堂的大份肠粉哪家更便宜，不辣 | 保留 B 食堂、大份、不辣等条件，比较符合条件的档口 |
| 上文已讨论鸡排饭，随后问“那哪家更便宜？” | 沿用鸡排饭及上文明确规格，不重复问菜名 |
| 哪里最便宜？且上文无餐品 | 只问要比价哪种餐品，不猜餐品或直接扫描所有菜 |
| 想吃鸡排饭 / 鸡排饭多少钱 / 预算 15 元吃什么 / 推荐便宜一点的晚饭 | 普通查询或推荐，不仅因“便宜”进入比价 |
| 不用比价，推荐一家鸡排饭 | 尊重否定意图，普通推荐 |

提取实际餐品关键词，去掉“我想吃”“帮我比价”“哪里的”“最便宜”“哪家价格最低”等请求用语，不把整句传入 `--dish`；`--dish` 始终是本次餐品名而非意图判断器。餐品不明确时先问要比价哪种餐品；已经给出餐品或类别则直接执行，宽泛类别须说明规格和配料可能不同。菜名中的“不要辣”应转成明确选项，而非混入菜名。本轮比价发起后可承接规格、预算和食堂范围修改，保留所有明确硬条件。

例如“哪里的鸡排饭最便宜”需大范围扫描时，按下一节先完整采集，再由模型判断鸡排饭候选；优先在持久内存中保留目录，只有内存保留与完整分页确实不可用时才使用带 `--state-dir` 的文件保底。“B 食堂的大份肠粉哪家便宜，不辣”保留 `--canteen B --option "大份" --option "不辣"`。成功直接获取时不重复运行脚本。查询多个明确食堂时分别带对应限制并合并结果；不能扩大为全校，也不能按只查一家得出两家比较结论。

## 全量采集与语义筛选

本参考和 `SKILL.md` 已提供正常查询所需口径，不预读其他参考或脚本源码。大范围比价统一先全量采集再交给模型筛选，不限于类别需求；只有明确要求菜名字面匹配时才使用下文 `compare.py`。零食、饮料、小吃、早餐等类别尤其不能使用 `--dish` 字面过滤。先采集全部店铺、全部菜品；由 LLM 结合商品分类、菜名、描述、规格和本轮语义逐项判断，之后再按已知整数分排序。平台分类是判断证据，不是唯一白名单；名称命中也不是充分条件。避免将套餐中提到的零食当作独立零食，把配料、加餐或不同分量当作同款。

据已知工具能力选择路线，正常查询不预先创建目录：原生工具能并发采集、在持久内存中完整保留并分页时直接使用。需要包内 Python 保底且环境有真正跨调用保留变量的代码内核时，用以下固定 API 在内存中完成采集、分页、时效检查与排序，不写数据文件：

```python
import runpy
import uuid

api = runpy.run_path("<技能目录>/scripts/catalog.py", run_name="campus_memory_catalog")
args = api["parser"]().parse_args(["--workers", "8"])
catalog = api["execute"](args, api["DINING"]["PublicApi"]())
snapshot_id = uuid.uuid4().hex
page = api["snapshot_page"](catalog, snapshot_id, "", 0, 32000)
```

示例中的采集参数须在 `execute` 前补上本轮真实的食堂、规格、预算和价格口径，避免遗漏条件。上述变量保留在同一个代码内核；后续用 `snapshot_page(catalog, snapshot_id, "", page["next_cursor"], 32000)` 逐页交给模型审阅，直到 `next_cursor` 为 null。这里的空 `snapshot_file` 仅表示没有文件，不是待读取的路径。全部审阅后，设置 `args.snapshot_id`、`args.select`、`args.reviewed_through = page["end_cursor"]` 及本次真实的排序、餐品条件，调用 `api["rank_snapshot"](catalog, args)`；后续追问用 `api["check_snapshot"](catalog, snapshot_id)` 检查时效。函数名通过上述 `api` 字典调用，不需要通读源码或临时写执行器。独立 PowerShell / Python 进程不共享变量，不能用于这条内存路线。

只有确认无法可靠保留内存与交付全量分页时，才选用下面的文件快照命令；此时再准备已允许的任务目录，需要时在该区域创建子目录，而非每次查询先建目录。`--state-dir` 必须指向已经存在且可读写的目录，脚本本身不自动创建。先确认所选目录可用，再全量采集一次，独立菜单最多 8 路并发。无目录权限时停止，不先抓完整结果再临时申请读取 `tool-output`，不编写 runspace、聚合或恢复脚本：

```text
python -I -S -X utf8 "<技能目录>/scripts/catalog.py" --workers 8 --state-dir "<已允许任务目录>"
python -I -S -X utf8 "<技能目录>/scripts/catalog.py" --read-snapshot "<返回的snapshot_file>" --snapshot-id "<返回的snapshot_id>" --cursor <返回的next_cursor>
```

`--option` 可重复，`--budget` 为元，`--now` 标记当前条件；这些条件仅生成价格或限制标记，不从目录中删除商品。内存与文件路线使用同一份完整目录和价格规则；不要调用会打印整个目录的旧式入口，也不把文件快照设为内存路线的前置条件。

直接获取时在同一持久工具会话中保留原始菜单，首次采集就记录每店成功／失败、商品数及空菜单，并保留分类、菜名、描述、所有规格、原价／优惠价、餐盒费、库存与可售字段。不要到最终写覆盖说明时才发现少了统计。读取成功菜单每店一次；失败项才重试。同次执行中筛选不准、换类别、排序计算或聚合出错只在这份数据上重算；后续用户请求的复用期限见下节。PowerShell 计算时用实际对象字段和数值，不依赖哈希表键的隐式属性聚合。

原始数据无需全部进入对话，但送给模型的紧凑目录必须包含所有有效商品及判断所需字段，不先关键词筛选或截取价格前 20 项。自动读完全部页面，模型为每页保留符合项的引用编号与必要说明，最后合并；未读取或未判断部分不能声称已完成语义筛选。不能把平台 `is_food=true` 当成“零食”等语义分类已通过。不要为缩短耗时减少覆盖，不承诺固定秒数。

### 后续请求与快照时效

按 [统一入口的菜单时效](../SKILL.md#菜单时效)：新查询重新采集，只有连续承接上一结果改条件且采集距今不足 5 分钟，才可复用；计时从 `queried_at_beijing` 开始，不从最后读文件或最后发消息开始。环境工具保留的数据也受此限制。原扫描范围不覆盖新食堂、当前营业 / 库存问题、明确刷新、跨日期或时间未知时重新获取所需范围。

对后续追问，内存路线用上述 `check_snapshot(catalog, snapshot_id)`，文件路线用下面的检查命令获取可靠当前时间及年龄；检查是只读操作，不联网、不改时间戳，也不要求将内存数据先导出：

```text
python -I -S -X utf8 "<技能目录>/scripts/catalog.py" --check-snapshot "<返回的snapshot_file>" --snapshot-id "<返回的snapshot_id>"
```

`status: pass` 且 `freshness.reuse_allowed: true` 才允许复用；`refresh_required` 表示过期、时间缺失或时钟异常，重新运行首次采集命令一次，随后只读新 ID。失败时说明刷新未成功；旧菜单仅可附原采集时间作为参考。不能因为上一轮表格仍在上下文里而跳过检查，不能声称该检查本身重新查询了平台。

检查仅决定下一次用户请求能否沿用旧数据。正在执行的同一次分页或排序即使超过 5 分钟，也继续读原快照直至完成，不反复重扫；页和排序均提供 `freshness`，完成时标明原采集时间与状态可能已变化。用户明确查看旧结果或只改格式可以保留历史数据，不称实时。

### 有界分页与模型选择

分页返回 `snapshot_id / snapshot_file / cursor / end_cursor / next_cursor / unit_count / item_count / records / freshness`。同一快照的内容哈希与 ID 必须一致；读取、筛选、排序均不重新联网。查询时间沿用快照采集时刻，不能把后续本地读取时间说成重新查询。`freshness` 不修改商品证据或哈希；它仅标明本次检查时的年龄与后续复用资格。

`records` 按原始顺序提供以下数组，保留所有商品及旧目录字段：

| 记录 | 解释 |
|---|---|
| `["catalog", header]` | 覆盖、价格口径、真实 URL、重试、采集耗时等全局信息 |
| `["shop", shop_index, context]` | 档口、状态、公共字段 `item_defaults` 及行内列名 `row_columns`；空菜单和失败店也保留 |
| `["item", ref, shop_index, row]` | 唯一引用编号；将该店公共值与按列名展开的 row 合并，得到完整商品 |
| `["fragment", record_index, part, parts, text]` | 单条记录过大时的完整 JSON 文本分片；part 从 0 开始，按序拼接所有 text 后作为一条记录解释，不忽略余片 |

`unit_count` 包括目录、档口和分片，不能当作商品数。持续读取真实的 `next_cursor`，直到 null；不自行猜下页，不要求用户发“继续”。每页预算默认 32000 个 UTF-8 字节（含换行），可设 `--max-output-bytes 8192` 等更低预算；平台若按 token 限制，还须适配其实际限制。脚本不靠截断字符串、删商品或价格预筛满足预算。

全部审阅后，模型将符合用户语义的 `ref` 传入固定排序命令，逗号分隔、连续编号可用范围；无符合项传 `none`。`--select` 使用 `["item", ref, ...]` 中的顺序引用号，不是商品 ID 或档口 ID；例如某商品 ID 为 98765、记录中的 `ref` 为 12，应传 `--select "12"`。不自己重写 JSON 展开或价格计算：

```text
python -I -S -X utf8 "<技能目录>/scripts/catalog.py" --rank-snapshot "<返回的snapshot_file>" --snapshot-id "<返回的snapshot_id>" --reviewed-through <最后一页的end_cursor> --select "<模型选择的ref清单或范围>" --intent meal --order desc --price-scope dish --limit 8
```

`--reviewed-through` 必须严格等于本次快照最后一页的 `end_cursor`，该值同时等于 `unit_count`，不能使用商品数或中间页游标。例如只有本次实际返回 `unit_count: 945`，且已读到 `next_cursor: null`、`end_cursor: 945` 时才传 945；这不是固定常量。该参数是模型声明的已审阅游标，脚本不能证明模型语义判断正确。

`desc` 为最贵，`asc` 为最便宜。餐品、吃饭或完整餐点默认用 `--intent meal`，排序会排除 `possible_addon_not_a_meal`；明确查零食、饮料、小吃或米饭、配料等单品时改用 `--intent items`，允许疑似配菜参加该次商品比较，但仍由模型逐项判断是否符合类别。两种模式只影响本地排序，不删采集数据、不重抓菜单。`--now` 要求采集时所有当前条件均得到支持，仍不代表实际结账成功。

`results` 仅限制展示；`ranked_count`、`winner_count` 和完整的 `winner_ref_ranges` 在全体已选候选上计算，不能遗漏并列价。比较口径改变必须重新算名次：菜价同为 97 元可以并列，含盒为 97.5 元与 98 元时就不再并列。不同餐品只作本次类别内价格排行，不据此宣称同款价差。

无参数旧 CLI 只返回短提示，不发网络请求；`--full` 是显式调试用的大输出。普通查询不追加 `ELAPSED_MS` 等文本，不使用 `Get-Content / ConvertFrom-Json` 解析长菜单；脚本已提供采集耗时与覆盖。确需用户授权后的原始文件恢复时明确按 UTF-8 读取，失败只报告错误类型和位置，不将整份损坏 JSON 输出。

### 目录输出

`shops` 按店铺分组，含 `id / name / canteen / platform_status / menu_status / returned_item_count / items`，空菜单仍保留该店，失败店与空菜单分开。顶层 `item_columns` 是完整字段清单；为减少重复文本，每店 `item_defaults` 保存该店所有商品相同的字段，`row_columns` 定义 `items` 每行数组的列。完整商品等于 `item_defaults` 合并 `dict(zip(row_columns, row))`，不猜列索引；共用默认值只是无损合并重复字段，不能当作缺失值：

| 字段组 | 含义 |
|---|---|
| `name / category / description` | 原始菜名、平台分类及纯文本描述；描述最多 500 字符，不能视为完整配料表 |
| `origin_fen / discount_fen / box_fen` | 原价、优惠价及餐盒费，单位为分，null 是未知 |
| `option_groups / selected_options` | 全部返回规格及本次选项，注明平台默认、用户指定或最低加价提议 |
| `dish_fen / with_box_fen` | 核算的菜价／含所列餐盒费估算；仍不含配送或未核实优惠 |
| `stock`、可售时段与限制字段 | 库存、售卖日、能否单买、食品标记、最小购买数量等原值 |
| `current_conditions_supported / blocking_reasons / unknowns / constraint_failures` | 当前条件、不可售原因、未知项及费用或规格障碍；不因有这些标记而删掉记录 |

`coverage` 含分组、分页、扫描、空菜单、失败和未扫描数，`platform_scope_scan_complete` 只代表本次平台返回范围。模型需要另行完成语义判断，不能把“采集完整”当作“分类已正确”。`retrieved_urls / failed_urls / retry_summary` 是真实来源和重试情况。

## 执行

优先由 LLM 按 `SKILL.md` 的接口速查表使用真实 HTTP POST 工具读学校分组、全部商户和菜单，在上下文里筛选、比较和整合回答；仅接口结构异常才查 [接口约定](api.md)。用户给出餐品就直接执行；不反复问是否要查全校，不要求“继续”。依赖分组和真实店铺 ID 的步骤先完成，再对独立菜单请求使用 4 至 8 路并发（默认 4 路）。逐店检查返回的所有菜品，不按店名猜是否售卖目标餐品，不因找到一家低价就停止。只并发独立请求，别把尚未取得的 ID 用作请求参数。

临时失败自动重试，每个请求最多 3 次，仅重试失败项，成功项保留；无匹配或空菜单不重试。登录跳转、401 / 403 不换登录态重试。扫描前发现工具不满足执行条件时，使用内置 `catalog.py` 保底；明确要求字面匹配才用 `compare.py`，不要求用户执行。菜单已成功采集后只补失败请求，不为本地计算错误或切换筛选方式重跑全部脚本。保底脚本也实现请求重试与 4 至 8 路菜单并发。成功直接读取后不额外运行 Python。下列命令仅用于明确菜名字面匹配的保底：

```text
python -I -S -X utf8 "<技能目录>/scripts/compare.py" --dish "鸡排饭" --summary --limit 8
python -I -S -X utf8 "<技能目录>/scripts/compare.py" --dish "肠粉" --option "大份" --option "不辣" --workers 8 --summary --limit 8
python -I -S -X utf8 "<技能目录>/scripts/compare.py" --dish "牛肉面" --budget 15 --price-scope dish --summary --limit 8
python -I -S -X utf8 "<技能目录>/scripts/compare.py" --dish "鸡排饭" --canteen B --now --summary --limit 8
```

默认实时读取平台返回的所有食堂分组，分页至店铺列表结束或全部分组店铺均已取得，遍历所有店铺及每店返回的完整菜品列表（含暂停店铺）；最后才对餐品名、规格和预算筛选、排序、展示。用户明确限制位置时保留 `--canteen`，不要因上一次普通推荐的位置而擅自缩小本次全校范围。接口本身遗漏、损坏记录或店铺菜单失败必须披露，不能将“平台返回范围已遍历”说成线下全校绝无遗漏。

`--dish` 为菜名的字面匹配，不自动扩展同义词，不以描述里提到某种原料作为同种餐品。用户说“面”一类宽泛名称时可以直接查，但必须说明各款配料、分量不同。无匹配时报告已查范围；需要改用其他关键词时说明原因，不把近义词结果冒充原菜名。

比价默认不再设置 12 页、108 个菜单的扫描上限，也不因连续三店失败跳过剩余店铺。失败店重试后记录缺口并继续其他店；分页失败或循环页则停止该分页链并明确未查全，不猜下一批店铺。`--max-pages`、`--max-menus` 仅在明确需要限制时使用，达到限制必须披露。`--workers` 默认 4、可设 1 至 8（通常选 4 或 8）；`--limit` 只限制排序后的展示条数，不影响全量扫描。无论 LLM 直接查询还是 Python 保底，都不得用普通推荐的菜单抽样代替比价扫描。

仅使用 `compare.py` 做明确菜名字面匹配时加 `--summary --limit 8`，只缩减展示与重复资料，完整扫描不变；输出若仍过大，不能默默读取未授权的工具输出目录。全量语义筛选用上述 `catalog.py` 分页，最终排序的 `--limit` 也只限制结果展示。正常不导出用户报告；菜单快照仅用于同次任务分页与重算，不跨任务自动当作实时缓存。

`--price-scope with-box` 默认比较“菜价加所列餐盒费估算”；`dish` 只比菜价。两个口径均不含配送、未知订单费用和未核实优惠。`--budget` 按所选口径过滤。缺少餐盒费不能按零算；可以展示已知菜价，但不能参与含餐盒费排序。`--option` 可重复；不能满足用户规格的商品单独列为不满足条件，不用其他规格代替。

`--now` 只将当前条件明确支持的餐品纳入比价候选，其他记录仍保留并解释原因。没有此参数时，也必须把营业、仅预订、暂停和未知状态区分展示；暂停的低价不能写成现在可买的最低价。

## 价格与同款判断

按整数分计价：有效 `discountPrice` 优先，否则 `originPrice`，再加各规格组所选 `money`；每组只选一项，用户明确规格优先，其次实际默认，无默认则标明最低加价提议；缺价或规格无法满足保留未知，零基础价且无可核实规格不称免费。菜价和餐盒费分列；缺餐盒费不得按零纳入含盒排序。正常查询无需读源码；复杂规格异常时才按需查看 [餐饮模块](dining.md)。同名餐品、实际所选规格标签相同且平台状态层级相同，才放入同一比较组；同名仍不保证配方、分量一致。不同菜名、套餐内容或大小份不得宣称完全同款，最多说明“符合用户要求的不同餐品价格”。

选项缺省时保留平台默认；没有默认而提出最低加价选项时，明确展示提议规格，不说用户已选择。基础价为零的商品必须加上实际规格价格；餐盒费单列。不将配菜、米饭或加料当作完整餐品。

价格未知、规格不满足、明确售罄、不可单买、非食品、最低数量超过一份或超预算的记录进入 `unranked_items`，不参与“最低已知价”或价差计算。`ranking_count` 为可比候选数，不能拿它代替已扫描菜单数。

`catalog.py` 不分配 `unranked_items`，通过 `excluded_reason_counts` 说明排序排除原因；商品目录仍包含全部记录。`possible_addon_not_a_meal` 是疑似配菜标记，`meal` 模式排除，`items` 模式保留供模型语义选择，不能把所有零食都当成不合格。输出 `meal_component_flagged` 保留该提示，未标记也不表示已验证完整正餐。`Pause / Prebook / Open` 分别保留暂停、预订、平台营业；其他时段或库存条件不明时不承诺现在可买。若类别内只有一家或是不同产品，说明“本次已查范围内符合该类别的最低已知标价”，不声称证明同款全校最低。

`comparison_groups` 按菜名、所选规格、平台状态分组，返回已知最低价、最高价、价差和最低价档口。即使分组覆盖完成，也仅能称“本次平台已查范围内”；有缺口时明确说“已查档口中”，不宣称全校最低价。`same_name_does_not_verify_equal_portions` 始终为真。

## 回答

结果标题明确写“食堂比价”，表格优先列：

| 食堂 / 档口 | 餐品与规格 | 菜价 | 餐盒费 | 所选口径估算 | 平台状态 |
|---|---|---|---|---|---|

按已知价格展示实际候选，同时保留状态差异和规格差异。只有同一比较组有至少两家不同档口时才给该组价差；不要从不同规格的全表首尾相减。营业条件未完全核实时使用“平台显示营业，其他条件未全核实”。

对“哪里最便宜”先指出本次已查范围内、满足规格及所选价格口径的最低已知价档口；并列最低要列出并列者，状态不同则分开说明。只有一家可比候选时说明“本次仅找到一家可比候选”，不能称已证明最低价；覆盖不完整时不得说全校最便宜。之后给比较表、覆盖和费用口径，保留 URL 清单与最后的快速预览。

末尾报告本次查询时间、食堂分组数量、成功扫描档口数、空菜单数、失败及未扫描数，以及价格是否包含餐盒费。空菜单与查询失败分开说；没有匹配不等于学校没有卖。

原始 JSON 仅用于核验，正常回答不显示内部 ID。直接获取和 Python 补抓均不可完成时说明无法进行相应实时比价，可分析用户提供的菜单快照，不能编造已扫完的结果。

随后按 `SKILL.md` 列出本次实际获取的完整 URL，最后追加“快速预览：” Markdown 表格，由模型提取主要可比候选、规格、所选费用口径和平台状态；不从不同规格或不同状态的候选中虚构价差。
