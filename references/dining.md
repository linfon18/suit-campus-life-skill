# 餐饮模块

## 能力与执行

数据源为学校餐饮平台的匿名只读接口，覆盖平台返回的档口，不保证等同于全校所有餐饮商户。每次默认重新查询，不把附带文件中的示例当作现售菜单。

默认先实时读取学校食堂分组，再用分组本次返回的档口 ID 查询商户列表。ID 不写死，基础状态为暂停的当前分组档口也能查看菜单。分组读取失败时允许回退到学校列表，并明确这是未按分组限定的范围。

优先由 LLM 使用真实 HTTP POST 工具按 [接口约定](api.md) 直接读取并在当前上下文筛选、整合结果。条件够用就一次回答，不先确认是否查询，不主动保存结果文件。临时失败自动重试，单请求最多 3 次；有效空菜单或没有匹配不算失败。直接读取重试后仍失败、工具不可用或关键数据无法可靠取得时，才用包内 `scripts/dining.py` 保底一次，沿用用户条件；脚本内部也自动重试。以下命令用于失败后的回退：

```text
python -I -S -X utf8 "<技能目录>/scripts/dining.py" shops --canteen B
python -I -S -X utf8 "<技能目录>/scripts/dining.py" menu --canteen B --shop "沙县"
python -I -S -X utf8 "<技能目录>/scripts/dining.py" recommend --canteen B --budget 15 --option "不辣"
python -I -S -X utf8 "<技能目录>/scripts/dining.py" recommend --budget 15 --now
python -I -S -X utf8 "<技能目录>/scripts/dining.py" recommend --budget 15 --exclude-shop "本轮已返回的商户ID"
python -I -S -X utf8 "<技能目录>/scripts/dining.py" queue --canteen A --shop "肠粉"
```

`--output-dir "<产物目录>"` 可为完整结果另存 JSON；不加时直接返回 stdout。只有代码内核时，用 `runpy.run_path("<技能目录>/scripts/dining.py", run_name="campus_life_dining")["main"]([...实际参数...])` 加载并调用，避免传入内核参数；同目录的 `probe.py` 必须一并保留。

正常查询不加 `--output-dir`，由 LLM 使用工具返回内容完成答复。下文默认 6 页 / 6 个菜单等范围只适用于普通选餐；进入比价后必须按 [食堂比价](compare.md) 遍历全部平台返回食堂、全部店铺和各店全部菜品，并对独立菜单使用 4 至 8 路并发，不能沿用普通推荐抽样。

全校零食、饮料等类别比价按 [食堂比价](compare.md) 的全量流程：一次采集全部商品，再由 LLM 判断符合项并排序，不把类别当作 `--dish` 关键词。首次采集即保留每店商品数、分类和空菜单；后续筛选、聚合、统计只重算本次数据，不重抓成功菜单。环境工具只有串行能力或无法交付完整证据时，在扫描前使用内置 `catalog.py` 保底。

直接获取与补抓的真实来源和覆盖情况要合并，不重复统计同一档口；仍有缺口则如实说明。缺少补抓能力或补抓失败时不无限重试，可分析用户提供的带时间菜单文件并明确不是实时结果。

## 参数与覆盖

| 参数 | 用法 |
|---|---|
| `shops / menu / recommend / queue` | 查商户、看菜单、按条件筛选、查询排队 |
| `--canteen` | A、B、C、紫荆、石榴，按实际返回的名称匹配；省略则不限制 |
| `--shop` | 本轮商户列表中的完整档口 ID，或档口名称的字面关键词；不是商品名 |
| `--dish` | 餐品名称或描述的字面关键词，不自动理解同义词 |
| `--budget` | 人民币元，单份单品的价格上限 |
| `--budget-scope dish / with-box` | 只算菜价 / 菜价加返回的包装费字段，默认后者；都不含未核实配送和优惠 |
| `--option` | 可重复指定确实需要的选项，如“不辣”“小份”；不能满足时不擅自忽略 |
| `--now` | 仅用于 `recommend`，只保留当前营业及商品时段等数据明确支持的候选；不保证可即时取到 |
| `--exclude-shop` | 可重复指定本轮已返回且需要排除的档口 ID，不按该参数查询任意 ID |
| `--max-pages` | 默认 6 页，每页 9 条，明确需要时最多 12 页 |
| `--include-unlisted` | 明确要求包含分组以外记录时使用；跳过分组限定，可能出现同名记录或未完成的较大列表 |
| `--max-menus` | 默认最多 6 个菜单；明确要求较大范围时可增至 48 |
| `--limit` | 默认显示 20 个商品或商户，最多 300；截断会在报告中标明 |
| `--output-dir` | 已存在且允许写入的产物目录；生成新的结果文件，不覆盖旧文件 |

先用位置和档口名称收窄范围。默认在不同食堂之间交错取样，并优先查询营业或可预订档口；达到菜单上限时说明仅扫描了这些档口。未扫描的菜单不能作为“没有符合餐品”的依据。

用户明确问“现在吃什么、现在能点什么”时使用 `recommend --now`。查完整菜单用 `menu`，不把未营业时仍可查询到的菜单隐藏成不存在。

`--dish` 是字面筛选，不适合直接塞进“清淡、低脂、管饱”等主观需求。先根据实际菜单描述判断，有证据才能说明匹配；热量、蛋白质和完整配料缺失时不虚构数值或做健康保证。

若用户明确问整个学校或某食堂的全部菜单，适当调高菜单和结果上限，并据报告判断是否完成覆盖。不要每次“吃什么”都拉全校菜单。

用户说“比价”，或表达“哪里的鸡排饭最便宜”“哪家牛肉面价格最低”“肠粉去哪买更便宜”等比较档口价格、寻找最低价的意图时，按语义转入 [食堂比价](compare.md)，不要求固定触发词。普通想吃什么、问价格或只希望便宜一点仍用本模块；结合上下文和否定表达判断。比价独立脚本会遍历本次平台返回范围，不使用普通推荐的六个菜单抽样作为全食堂结果；直接获取失败或缺少 FETCH/POST 工具时保留 `compare.py` 作为最后保底方法。

若硬条件没有候选但 `menus_unscanned` 仍大于零，可以将菜单上限扩大后再查一轮，通常从 6 增至 12，具体食堂可按实际匹配档口数取值。两轮仍未完成覆盖时说明剩余范围，不为了凑推荐擅自放宽条件。

## 价格和选项

- 金额以分存储，显示为元；脚本计算用整数，保留所用原始字段和选项。
- `discountPrice` 有效时优先使用，缺失或无效时退回原价；零值不能当成字段缺失。
- 每个选项组明确选一个选项。优先使用用户指定，其次实际标记的默认选项；没有默认时提出该组最低加价的选择，并用 `selection_source` 标注为提议。提议不等于用户已经选择。
- 同组要求了互斥的两个选项、所需选项不存在、选项字段结构异常或价格未知时，筛选不能视为满足。`menu` 模式仍可展示该商品供核对。
- 菜价为基础价格加各组选项的 `money`。不套用拼团价、会员价或未核实优惠。
- 基础价为零而没有可核实规格时，标为价格未核实，不称免费。
- 包装费单列。`with-box` 仅检验“菜价加字段所列包装费”的估算，不表示费用一定适用，也不包括配送。
- 严格“总共 15 元含配送”不能靠这个估算保证。明确列出仍未核实的费用，不能把符合菜价预算写成符合到手总预算。
- 脚本按一份单品计算，不构造跨档口合单、套餐拼接或自动下单。用户要求组合时，基于真实规格另行按整数分核算，并考虑单店订单费用。

## 状态与筛选解释

列表 `openStatus` 的 `Open / Prebook / Pause` 分别保留为“平台显示营业 / 仅预订 / 暂停”。`status: Open` 不等于当前营业。

汇总分开返回 `coverage.shop_status_counts`（原始 `status`）和 `coverage.shop_open_status_counts`（原始 `openStatus`），各自包含未知数；统计范围是本次商户列表在用户筛选之前的全部已返回商户，不混读两种状态。判断当前平台营业以 `openStatus` 和相应时段等证据为准，基础 `status` 不能代替它。

`recommend` 只从 `Open / Prebook` 选商户；`--now` 进一步只选 `Open`。`menu` 和 `shops` 仍可查看暂停档口的真实记录，不能把暂停档口推荐为当前可购买。

脚本用北京时间核对商户及商品的 `saleTimeRange`，支持跨午夜和 `24:00`，无法解析则为未知。`--now` 还要求商品 `saleOnTime` 明确为真、没有显式售罄和不可单买限制。仅预订档口的推荐要求商品 `saleOnBook` 明确为真。非全周的 `shipDays` 语义尚未验证，不能据此确认当前可点。

“当前条件数据支持”也不保证实际下单成功或即时取到。商品限购、最低购买数量、商户必买分类等结算规则可能仍需平台确认；不能将推荐当作结算结果。

只有真实选项存在“不辣”才能用 `--option 不辣` 筛选并说明“可选不辣”。没有标注辣度不能猜测不辣。过敏原、完整配方和交叉接触均不能仅凭菜名或选项保证。

脚本会排除明确不可独立购买和非食品的单品，并标记疑似配菜。最终推荐必须结合实际分类、名称和描述审阅，不能把米饭、加料或餐具作为一顿正餐。用户明确查配菜或饮品时用 `menu` 模式查看，不称其为完整正餐。

疑似配菜标记仅是保守提示，不能证明其余商品就是完整正餐。预算选餐仍需模型结合分类、名称、描述和规格审阅。未匹配档口时返回 `no_matching_shop` 与 `shop_selection`，不请求任意 ID；网络失败仍保留错误，不能说成档口不存在。推荐无候选返回 `no_recommendations`，先看菜单覆盖和排除原因。

取餐方式字段只展示实际原值。`takeAway / takeOut / eatIn / eatInTake` 等字段未完整验证语义，不自行映射“支持送宿舍”“支持堂食”等承诺。

## 结果解读

脚本返回：

- `source`、`queried_at_beijing`：数据类型与本次时间。
- `coverage`：商户列表是否翻页结束、筛选后商户数、菜单成功数、未扫描数量和商品截断情况。
- `shops`：实际匹配并返回的商户。
- `items`：商品原始公开字段、所选规格、价格、营业判断及未满足条件。
- `queues`：排队结果，只有返回真实数值才算已知。
- `requests`：真实请求的方法、路径、HTTP 状态、业务码及数据存在性；没有凭证。
- `errors`：真实失败和缺口。

`coverage` 的列表翻页结束不表示全校商户绝对齐全，只表示本次查询范围在接口中结束。重复页面或达到页数上限均不算完成列表覆盖。

查询失败和空菜单分开说明。没有满足条件时解释排除原因或数据缺口，不拿猜测候选凑数。用户要求“换一家”时继续带上原硬条件并排除上次档口；需要扩大范围可以在下一次查询中调高上限，但不能说之前已经查过。

## 排队

`queue` 模式最多读取两个匹配商户的队列，不抓菜单。返回没有 `data`、只有部分字段、字段为 null 均表示数据未完整取得。真实零值可以保留，但不代表现场无需等待。

`mealTime` 只是平台平均出餐时长，不能改名为前方排队时间。平台队列是否包括现场、品牌小程序、其他平台尚未核实。

## 推荐回答

先给 2 至 3 个实际匹配候选，说明“档口 / 餐品与所选规格 / 菜价与包装费估算 / 平台状态 / 匹配点或未知项”。对没有完全满足条件的候选另列说明，不混充达标。

末尾用一行说明查询时间、扫描几个档口以及费用口径。正常回答不展示内部 ID；用户要求核验时才显示对应真实 ID 和请求证据。需要用户打开平台确认时使用已知平台入口，不拼接未经验证的点单深链。

随后按 `SKILL.md` 列出本次实际获取的完整 URL，最后追加“快速预览：” Markdown 表格，由模型提取食堂 / 档口、餐品 / 规格、费用、平台状态和注意事项；只用已核实数据，未知费用或状态不补造。
